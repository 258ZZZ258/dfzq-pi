# 三类审计报告逐句可变内容、数据来源与处理逻辑说明

> 版本：V6.35（补充3.6、3.8和3.9的LLM归纳逻辑）
> 日期：2026-07-28
> 原则：模板正文和批注是第一依据；每处模板原句完整呈现；核对版Excel作为二手核对材料；当前模拟单独说明；正式接口尚未明确时只写“生产最小数据要求”，不冒充现有系统字段。

## 一、建设目标、数据边界与端到端工作流

### 1.1 建设目标

本方案面向营业部常规审计、反洗钱审计和负责人离任审计三类报告。系统接收用户创建的报告任务，按报告类型读取相关业务系统记录和上传文件，完成数据校验、规则计算、条件段落选择、有限度的语言生成、Word草稿排版和逐主张评测；整份报告生成后再由审计人员统一复核和定稿。

数据和规则的采用顺序为：

1. Word模板正文确定报告结构、原句和格式。
2. Word批注确定条件保留/删除、数量词、排名区间和审计判断边界。
3. 字段来源核对版Excel用于核对数据归属、获取方式和校验要求。
4. 当前模拟文件用于验证读取、计算、生成和评测链路，不代表相应生产接口已经接通。

本文仅分析会随营业部、人员、期间、经营数据、审计发现或审计判断变化的正文位置。完全固定且不存在条件分支的标题、章节名称、落款和通用整改结尾不单独展开。

### 1.2 数据边界

1. **正式系统原始数据**：来自审计、人力、OA、财务/经营、合规、反洗钱、信访纪检、法律、信息技术和投诉等系统或部门台账。
2. **正式上传文件**：包括经营数据Excel、租赁合同、营业执照、制度文件、审计底稿、监管函件、培训资料和其他证明材料。
3. **当前模拟数据**：位于 `packages/task-runtime/fixtures/audit-report/source-simulation`，其中：
   - 报告任务输入文件只用于模拟用户创建任务后的入口参数；
   - `模拟审计系统数据.xlsx`由模拟服务加载并通过HTTP接口返回项目、机构、人员、OA发文、审计发现、整改、风险、反洗钱和绩效等记录；
   - `模拟经营数据.xlsx`按用户上传经营Excel的方式直接解析。
4. **生产最小数据要求**：正文后续列出的生产字段是生成相应句子所必需的业务含义，不表示现有生产接口已经使用相同字段名。

### 1.3 端到端工作流

1. **用户创建报告任务**
   用户选择报告类型、营业部、审计期间；离任报告还需选择被审计人员。系统生成唯一任务编号，记录模板版本和创建人。任务编号用于串联后续取数，不代替用户创建项目。

2. **确定报告数据范围**
   常规和反洗钱报告按审计起止日取数；离任报告以OA任免发文确定的任职起止日为主。任务输入与OA、人力或审计项目记录冲突时停止自动定稿，将冲突记录为待复核项。

3. **按数据源分别取数**
   系统使用机构编号、人员编号、项目编号和期间查询各数据源。不同系统的记录先保持原貌，不在取数阶段拼接成报告句子。查询同时保存来源系统、记录编号、查询时间、查询范围和查询是否完整。

4. **解析上传文件**
   经营Excel按机构代码、指标名称和双层期间表头解析；租赁合同、制度文件和底稿附件提取候选字段并保留文件编号、页码或证据位置。文件解析结果必须经过格式校验；无法确定或相互冲突的结果标记为待复核，不在字段层面单独设置人工确认流程。

5. **统一业务主键和口径**
   机构统一使用内部机构编号，人员统一使用员工编号，审计问题统一使用问题编号。名称、简称、指标同义词和期间格式通过字典映射；空值和数值0保持区分。无法唯一映射的记录不自动合并。

6. **形成可追溯事实层**
   每个事实保存“业务值＋来源记录＋适用期间＋数据状态”。例如员工人数对应人力快照，任职期对应OA发文，经营排名对应Excel单元格，问责事项对应合规台账，反洗钱问题对应业务明细和审计底稿。

7. **执行确定性规则**
   日期格式、人数、金额、排名、盈亏、五等分排名区间、问题数量词、章节编号、字段替换和条件段落选择由规则完成。缺数、冲突或查询失败时，规则输出阻断项，不把缺数解释为0或“未发生”。

8. **有限使用LLM**
   LLM处理规则无法稳定完成的语义任务，包括从完整审计问题原文中识别标题、制度依据、事实描述和内部子项，以及结合多个已核验事实形成简洁叙述、审计问题归纳和整改建议组织。传给LLM的输入必须限定为当前任务已经取回并带来源的问题原文或事实集合，不允许整库自由检索。LLM不得修改数值、日期、名称、文号、问题事实、制度名称、重要性等级和固定模板文字，也不得自行判定问题是否属于“较大问题”。

9. **生成报告草稿**
   系统将规则结果和LLM结果填入受控Word模板，按条件保留或删除句子和段落，重新连续编号，并应用字体、字号、颜色、表格、分页和全角中文标点规则。缺失、冲突或低置信度结果不触发生成前人工确认，系统仍先生成完整草稿，并在对应位置及复核清单中标记“待复核”。

10. **人工复核与定稿**
    人工不介入字段级生成过程。系统生成整份报告后，由审计人员统一复核来源证据、条件分支、审计判断、敏感事实、LLM生成文字、待复核项和Word格式，并直接在报告中修改、定稿。系统只保存最终复核状态、复核人、复核时间和修订版报告，不要求逐字段留存人工确认记录。必要反馈或审批未完成时不得出具正式报告。

11. **执行严格Rubric评测**
    评测程序按第五章规则提取报告中的每个可变主张，逐项与人力、OA、经营、审计、合规、反洗钱等原始记录核验；同时检查模板固定文字和Word格式。任一原子主张缺少证据、值不一致或条件分支错误，该项记0分。

12. **归档生成证据包**
    定稿时归档报告文件、任务输入、原始数据快照、上传文件清单、字段溯源表、规则版本、模型版本、最终复核记录、修订版报告和Rubric结果，确保报告可以重放和复核。

## 二、常规审计报告

### 2.1 标题、称呼和引言

**模板完整原句**

> XX证券营业部
> XX证券营业部：
> 按照审计工作安排，审计中心于2026年X月成立审计组，对你单位2023年X月至2026年X月期间（以下简称“审计期”）经营活动和内部控制的适当性、合法性和有效性等情况进行了审计。

**逐字段来源和规则**

| 可变字段 | 正式数据来源 | 来源系统/文件 | 获取方式 | 自动 | 生成规则 | 校验规则 | 当前模拟来源 | 所需业务字段及期望形态 |

**具体处理**

1. 主要收入来源只在收入构成项中比较：代理买卖证券业务净收入、客户保证金利息净收入、产品相关收入、两融息差净收入、其他收入；不把总项“考核收入”和费用项“业务管理费”放入候选。
2. 每个期间取金额最大的收入构成项。多个期间结果一致时写“以XX为主要收入来源”；不一致时按期间分别概括，不强行输出单一来源。
3. 排名分档按Word批注五等分。计算 `band=ceil(rank×5÷participants)`，结果1至5分别对应上游、中上游、中游、中下游、下游；名次从1开始，超出参与家数视为异常。
4. 多指标处于同一档时可以合并为“其余各项基本处于中游”，但必须逐项先计算，不能用“其余”覆盖缺失排名。
5. LLM只允许把已经计算好的主要收入来源和排名分档组织成模板句，不得增加盈亏、同比趋势或其他模板没有要求的经营分析。

**具体处理**

本节采用统一原则：规则负责查询完整性、硬条件、状态、责任和冲突检查；LLM负责把问题映射到六领域、归并同一事项、推荐段落模式并基于已核验事实生成摘要。段落模式、事项重大性和“较大缺陷”等审计判断必须有底稿或正式结论支持。

对六份人工常规报告的复核显示，2.5实际存在三种第一段写法：深圳、西安、贵阳采用常规正面型；上海徐汇采用整体负面型；上海浦东启帆和汕头采用简化型。人工报告中已结但具有重要性的劳动仲裁及诉讼仍可能披露，因此诉讼不能只按“是否未决”机械处理。

1. 第一行先确定第一段模式，再处理六领域。常规正面型中六领域默认写全，出现批注明确的较大问题时删除对应领域；整体负面型中的六领域是审计覆盖范围，可以完整列示；简化型不生成六领域结论。LLM可以依据问题分布和证据提出模式建议，但最终使用哪个模式以及“未发现重大异常/内部控制较为薄弱”等结论由底稿控制。
2. 第二行对应模板第二句中的信息安全事故、重大突发事件、未决诉讼和未了结客户投诉。每类单独查询并决定否定短语和事项段落；投诉按“未了结必写、已了结普通可不写、重大事项不论是否了结都写”处理。已结普通诉讼通常可不写，但底稿认定重要或需要说明完整处理过程时仍可披露。
3. 第三行对应模板第三句：有问责时按事项、人员、责任和措施生成；无问责时整段删除。员工被合规问责时，常规正面型第一段同步删除“员工执业行为管理”；整体负面型不因该问责删除作为审计范围列示的领域。
4. 第四行是外部检查、监管函件或关注函条件段。存在合规问责段时排在合规问责之后；不存在合规问责段时排在重大异常事项及相关投诉段之后；始终位于2.6之前。
5. 第五行是综合评价。合规问责段和外部检查/监管事项段均已生成时，在全部事项之后另起一段固定写“上述情况反映出营业部相关内部控制和合规管理存在较大缺陷。”并删除或改写前文“未发现重大异常”。
6. 最终段落顺序为：第一段内控结论—第二句重大异常事项总述—合规问责—外部检查、监管函件或关注函—综合评价。某类不存在时直接跳过，不生成空段。

**具体处理**

本节严格按报告正文顺序生成，不再把第一句话拆成多张彼此独立的判断。

1. 先确定负责人。用审计任务中的负责人编号取得姓名和有效任职记录，一次性替换三处“XX同志”。
2. 再生成第一评价句。六份人工常规报告体现出三种分支：

   - 完整常规型：底稿支持正面评价，各项查询完整且无冲突，生成模板完整句。
   - 调整保留型：总体仍可作正面评价，但部分否定短语或结论不成立，删除冲突内容并按底稿增加保留意见。上海浦东启帆删除了“未发现重大违法违规事项”，贵阳增加了“但在……方面有待加强”。
   - 特殊事项型：负责人本人存在多起或严重事项，第一评价句整体不再成立，整句删除，改在后面逐项披露事项。上海徐汇采用这一模式。

3. 然后生成第二评价句，分开处理前后两部分：

   - “能够/基本能够执行公司有关经纪业务的重大经营决策”由财富委反馈和审计底稿决定，不能由经营排名或负责人绩效等级推导。
   - “积极/平稳开展业务”复用2.4已经核验的营业部综合业绩排名结论：处于上游或中上游，即排名比较靠前时写“积极开展业务”；处于中游、中下游或下游时写“平稳开展业务”；各项指标分化较大或综合结论不明确时，使用财富委或底稿确认的表述。

4. 接着生成绩效句。按负责人编号取得已生效年度绩效，按年度升序写入；缺失年度不补省略号。
5. 最后处理个人信访、投诉、举报和案件。有事项时在前三句之后另起段，按时间顺序写来源、事项、调查结论和处理结果；同时删除前文所有相冲突的否定或正面表述。
6. 规则负责人员匹配、查询完整性、否定短语开关、冲突检查和绩效排序；LLM负责在规则允许的范围内选择句式、归并同一事项、概括保留意见和润色。LLM不得自行生成“基本能够”“未发现重大违法违规”或改变调查结论。

补充说明：人工报告中出现的“其个人及其所在营业部未受到过监管部门或公司内部的处罚”不是模板必写句。只有个人、营业部以及监管、公司内部四个查询维度均完整且均无处罚时才可加入；不满足时直接不写，不需要另造替代句。

2. 再读取前次项目的全部问题及整改记录。不能只查询状态为“未整改”的问题，否则无法证明“均已整改”。
3. 对每个前次问题分别判断：

   - 状态不是已完成，或者缺少必要整改、验收依据：属于未完成整改；

5. 全部前次问题均有效整改时，原样输出“前次审计发现的问题均已整改，本次审计未发现同类问题。”任一问题未完成或未有效整改时，整句删除，只写例外问题；一个问题用中文双引号列出原问题标题，多个问题可以归纳列示。
6. 前次项目、整改记录或本次问题查询不完整时，本节标记数据未就绪，不得输出“均已整改”或“未发现同类问题”。

2. 先生成章节引言和分类标题。直接使用审计系统“问题分类”字段，不做二次映射，也不由LLM重新分类。分类按其在问题列表中首次出现的稳定“序号”排列并编号为“（一）（二）……”，同一分类内按列表序号升序生成问题编号；不再假设系统存在独立的“报告分类规则”或“报告展示顺序”字段。
3. 每项问题按正文顺序生成三个部分：

   - 问题标题：由LLM根据问题细分和核心事实生成简短标题；

   - 事实描述：以详情页“审计发现问题”为主，结合底稿样本明细，由LLM整理语序，但所有日期、对象、数量、状态和影响必须原样受控。

4. LLM参与范围是标题生成、同一事实去重、制度依据句式整理和事实段润色；问题分类完全采用系统原值，不使用LLM。规则负责问题全集、字段完整性、分类顺序、编号、数值锁定和缺失门禁。LLM不得生成源数据中不存在的制度、数量、责任、影响或整改结果。
5. 任何问题缺少完整“审计发现问题”时不能进入正式报告；缺少制度依据时，该问题事实可以进入待补材料状态，但不能生成完整的正式报告问题段。系统应提示缺少哪条问题的哪项材料，而不是整章静默遗漏。

**具体处理**

1. **选择结论分支。** 先检查是否存在已经正式确认的重大违法违规事项或重大内控缺陷。不存在时使用固定模板；存在时进入重大问题分支。问题数量只用于“个别/部分”，不能用于判断是否重大。
2. **处理普通问题数量词。** `findingCount` 按报告实际披露的不同问题编号去重，1—2项写“个别问题”，大于2项写“部分问题”；不按客户数、样本数或 `issueCount` 累加。0项且无重大事项时进入4.6无问题版。
3. **由LLM改写重大问题结论。** 删除整句“未发现重大违法违规事项或重大内控缺陷”，将营业部全称、重大类型、已确认重大问题、正式审计判断及其他问题数量输入LLM，生成与4.4问题内容一致的专项结论；普通问题是否需要在结论中同时概括，由LLM基于已披露问题组织，但不得遗漏重大问题。
4. **自动校验并生成草稿。** 规则检查结论是否残留“未发现重大……”等冲突表述，以及每项重大判断能否回溯来源。存在冲突或低置信度时仍生成带标记的完整报告草稿，人工在报告生成后统一审核和定稿。

## 五、严格Rubric设计与执行

### 5.1 评测目标和输入

Rubric用于回答三个问题：

1. 报告中的每个可变事实是否与原始系统记录一致；
2. 应出现的可变内容是否完整出现，条件句和条件段落是否选对；
3. 生成后的Word是否保持模板结构、固定文字和格式。

一次评测必须同时输入：

1. 待评报告DOCX；
2. 与生成时相同版本的Word模板；
3. 报告任务输入和模板版本；
4. 本次生成使用的原始数据快照或可重放接口响应；
5. 上传文件及其文件编号、工作表/页码等定位信息；
6. 字段溯源记录、规则计算中间结果、审计问题领域映射记录、最终复核记录和修订版报告；
7. 生成程序版本、规则版本和模型版本。

人工报告不是事实真值。人工报告只用于检查机器报告相较人工报告是否漏掉章节、事实类型或必要说明，以及表达和版式差异；事实正确性仍以原始系统记录、上传原件和审计底稿为准。

### 5.2 评分对象：从句子拆成原子主张

评测程序不按“一整段大致正确”打分，而是把每个可变句子和表格单元格拆成最小可核验主张。一个句子包含三个事实时，必须生成三个评分项。

原子主张分为六类：

| 主张类型 | 示例 | 核验方式 |
| --- | --- | --- |
| 字段值主张 | “营业面积428平方米” | 与对应来源字段精确比较 |
| 关系主张 | “卢俊同志任上海浦东新区启帆路证券营业部负责人” | 同时核验人员、机构、职务和有效期间 |
| 计算主张 | “股基交易量处于上游” | 用源排名和参与家数重新计算 |
| 存在/否定主张 | “未发生未决诉讼” | 核验完整查询已完成且结果为零 |
| 条件分支主张 | 有问责时删除“员工执业行为管理” | 核验条件、选中的模板分支和被删除内容 |
| 审计判断主张 | “较为有效”“基本能够”“未发现重大内控缺陷” | 核验审计底稿、相关事实和正式审计结论 |

经营表格中每个金额、排名、期间、单位和备注分别形成评分项；审计问题中每个问题的标题、制度依据、事实、总体数、样本数、异常数和状态分别形成评分项；多个问题不得合并成一个分数。

每条评分记录至少保存：

| 字段 | 数据形态 | 示例值 |
| --- | --- | --- |
| `rubricItemId` | 字符串标识 | SF-REG-FINDING-F-001-FACT |
| `reportType` | 文本 | regular |
| `reportLocation` | 文本 | 二、审计发现的主要问题/（一）/1 |
| `claimText` | 文本 | 抽查21笔业务，其中1笔影像不规范 |
| `claimType` | 文本 | 字段值主张 |
| `expectedValue.population` | 整数 | 21 |
| `expectedValue.exceptions` | 整数 | 1 |
| `actualValue.population` | 整数 | 21 |
| `actualValue.exceptions` | 整数 | 1 |
| `sourceRefs[].system` | 文本 | 审计系统 |
| `sourceRefs[].recordId` | 字符串标识 | F-001 |
| `sourceRefs[].field` | 文本 | factText |
| `sourceRefs[].fileId` | 字符串标识 | WP-001 |
| `sourceRefs[].location` | 文本 | 样本清单第1—21行 |

### 5.3 0/1判定规则

每个适用项只能记0分或1分，不给0.5分。

记1分必须同时满足：

1. 报告中的主张能够唯一对应到指定来源记录；
2. 来源查询覆盖正确机构、人员和完整期间；
3. 原始值、计算结果或审计底稿结论与报告完全一致；
4. 该主张适用的条件分支选择正确；
5. 不存在与其他报告段落相冲突的主张。

出现以下任一情况记0分：

1. 数值、日期、名称、文号、等级、状态或数量不一致；
2. 没有来源记录，或只引用生成后的汇总文字；
3. 查询失败、权限不足、分页不完整或期间不完整，却写成“无事项”；
4. 使用错误机构、错误人员、错误项目或错误期间的数据；
5. 计算公式、单位、同义词映射或空值处理错误；
6. 审计判断缺少审计底稿或正式审计结论支持；
7. 应出现的主张缺失；
8. 不应出现的条件句、段落或问题被生成；
9. LLM增加原始数据没有支持的原因、影响、评价或整改措施；
10. 同一事实在报告不同位置互相矛盾。

`N/A`仅用于模板规则明确不适用的内容。例如经纪人数为0时，“证券经纪人X名”正确删除，该项记为条件分支通过，不把不存在的字段值主张列为适用项。应当出现但漏写的内容不能标为`N/A`。

### 5.4 Rubric执行步骤

1. **读取并渲染报告**：解析DOCX段落、表格、文本运行、颜色、字体、页眉页脚和分页，并渲染为页面图片检查视觉结果。
2. **建立模板变量清单**：根据本说明第二至四章，列出该报告类型所有可能的变量槽位、条件句和条件段落。
3. **计算期望内容**：只用原始数据、确定性规则、受控领域映射基准、审计底稿和正式审计结论重新计算期望值，不读取机器报告的结果反推答案。
4. **提取实际内容**：规则优先提取标题、日期、数字、表格和问题结构；仅在复合自然语言段落中使用LLM拆分原子主张。
5. **逐主张对齐**：使用机构编号、人员编号、问题编号、指标代码、期间和来源记录编号对齐；禁止仅凭语义相似度把不同记录视为同一事实。
6. **执行字段核验**：名称、日期、金额、排名、数量、文号和状态精确比较；经营派生判断按相同公式重新计算。
7. **执行否定主张核验**：对“未发生、未发现、均已、及时、有效”等词，检查所有必需来源均已完整查询。
8. **执行条件完整性核验**：比较期望段落集合和实际段落集合，检查应保留、应删除和二选一分支。
9. **执行跨段一致性核验**：比较概况、基本情况、问题、意见和结论中引用的同一事实。
10. **执行Word格式核验**：检查模板固定文字、标题层级、编号、字体字号、负数颜色、表格结构、日期及全角标点。
11. **生成结果**：输出总分、三类分项分、每个0分项的报告位置、原始证据、期望值、实际值、失败原因和责任分类。

六领域映射采用以下专项核验规则：

1. 能由映射字典唯一确定的审计问题，期望领域直接由确定性规则计算。
2. 需要LLM语义分类的问题，评测时不得再次调用生成阶段的同一个LLM并把其输出当作真值；应使用已评审的领域映射基准或审计底稿中的正式领域结论。
3. 评测基准至少保存问题记录标识、源问题分类、问题细分、问题类型、审计发现问题原文、期望六领域标签和支持标签的原文证据片段。
4. LLM输出的证据片段必须能够在源字段或问题原文中逐字定位；无法定位、标签超出六领域或只依据宽泛分类名称推断多个领域时，领域映射项记0分。
5. 领域分类和严重程度分开评分。领域分类正确不代表问题属于“较大问题”；是否删除领域必须另外核验重要性、监管处罚、问责、损失影响、严重程度规则或审计底稿结论。
6. 没有领域映射基准且规则不能唯一分类时，该问题不得被当作已确定映射生成正式结论；报告应保持待复核状态。

| FM-01 | 固定文字 | 除已批准的条件删除外，与模板文字一致 |
| FM-02 | 标题和层级 | 报告标题、一级至三级标题的名称和层级正确 |
| FM-03 | 编号 | 中文章节号、括号序号和阿拉伯数字连续，无跳号重号 |
| FM-04 | 段落顺序 | 可变段落位于模板规定位置 |
| FM-05 | 字体 | 正文、标题、表格数字字体符合模板 |
| FM-06 | 字号 | 正文、标题、表格数字字号符合模板 |
| FM-07 | 字形 | 加粗、缩进、行距和段前段后符合模板 |
| FM-08 | 表格结构 | 表号、行列数、表头、合并单元格和边框符合模板 |
| FM-09 | 数字格式 | 金额千分位和小数位、排名整数、KPI格式正确 |
| FM-10 | 负数格式 | 负号保留且负数按批注标红 |
| FM-11 | 日期格式 | 使用`YYYY年M月D日`或对应年月格式，不补零 |
| FM-12 | 中文标点 | 句号、逗号、冒号、分号和括号使用全角中文形式 |
| FM-13 | 文号格式 | 括号内文号、方括号、年份和字号与原发文一致，且文号所属发文序列与正文发布主体一致 |
| FM-14 | 分页 | 标题、表格和问题段落无明显错误分页或孤行 |
| FM-15 | 空白和占位 | 无多余空段、空表、说明括号和模板提示文字 |
| FM-16 | 落款 | 落款主体和位置符合对应报告模板 |
| FM-17 | 报告日期位置 | 日期位于模板规定位置且对齐正确 |
| FM-18 | 敏感信息 | 客户等敏感信息按规则脱敏，无无关原始标识 |
| FM-19 | 无额外生成内容 | 不存在模板和已核验事实之外的扩写 |
| FM-20 | 页面视觉复核 | 渲染页面无截断、重叠、乱码、字体替换和异常留白 |

C类得分：

`格式得分 = C类通过项数 ÷ C类适用项数 × 20`

### 5.8 总分、门禁和结果分级

总分采用100分制：

`总分 = 事实一致性得分 + 条件完整性得分 + 格式得分`

结果分级：

| 总分 | 结果 | 含义 |
| --- | --- | --- |
| 95—100 | 高完成度 | 可进入最终人工复核 |
| 85—94.99 | 基本可用 | 存在少量需修正项 |
| 70—84.99 | 不完整 | 需修改后重新生成和评测 |
| 0—69.99 | 不可用 | 关键事实、分支或格式存在明显问题 |

无论总分多少，出现以下任一门禁失败，报告不得标记为“可定稿”：

1. 报告类型、营业部、被审计人员或审计/任职期间错误；
2. 任何金额、排名、问题事实、问责、处罚或可疑交易数量与原始记录不一致；
3. “未发生、未发现、均已、及时、有效”缺少完整来源支持；
4. 存在重大违法违规、重大内控缺陷或重点可疑交易但报告遗漏；
5. 审计判断缺少审计底稿或正式审计结论支持；
6. 报告仍含占位符、模拟标识错误或无法正常打开/渲染。

### 5.9 人工报告对比

人工报告对比在严格源数据评分之后执行，不覆盖源数据核验结果。

1. 将人工报告和机器报告按模板章节对齐。
2. 提取双方出现的问题、风险事项、经营判断、结论和建议。
3. 列出机器报告相对人工报告的遗漏项、新增项、合并/拆分差异和措辞差异。
4. 对每个差异回到原始数据判断：人工报告遗漏但原始数据支持的，不扣机器事实分；机器新增但原始数据不支持的，机器对应主张记0分。
5. 格式差异按FM类项目评分；纯表达差异只作为诊断，不因“与人工措辞不一样”直接扣事实分。
6. 输出“源数据正确性”和“人工报告完成度对比”两个独立结果，避免把人工报告中的历史遗漏当成标准答案。

### 5.10 失败原因分类与修正闭环

每个0分项必须归入以下一种原因：

| 失败类型 | 判断标准 | 修正责任 |
| --- | --- | --- |
| 实现问题 | 原始数据和规则足以得出正确结果，但程序取错、算错、漏写、分支选错或格式错误 | 修改取数、规则、模板渲染或提示词 |
| 数据问题 | 必需原始记录缺失、期间不完整、接口失败或多来源冲突，无法证明主张 | 补数据、补接口、补材料或完善审计结论 |
| Rubric问题 | 评分项使用了错误来源、错误口径、错误条件或与模板批注冲突 | 修改Rubric定义并重新评测所有受影响报告 |
| 模板问题 | 模板正文、批注或格式自身存在冲突、半角符号或占位不一致 | 形成受控模板新版本并记录变更 |

修正流程为：

1. 保存失败项的实际报告内容、期望值和来源证据；
2. 确认是实现、数据、Rubric还是模板问题；
3. 只修改对应层，不通过放宽Rubric掩盖实现错误；
4. 重新生成受影响报告；
5. 对全部三类报告执行回归评测；
6. 保存修改前后分数和失败项变化。

### 5.11 当前模拟评测边界

当前模拟可以验证任务创建后的数据串联、Excel解析、规则计算、条件分支、报告生成和Rubric执行，但下列主张缺少真实原件或正式多部门记录。在严格Rubric中，这些主张不能因模拟汇总值存在就直接记1分：

1. 营业面积对应的租赁合同原文和页码；
2. 营业执照及工商名称交叉核验；
3. 合规、财富委、纪检信访、法律、信息技术、客服和营业部的原始回函或台账；
4. 独立版本化制度库；
5. 反洗钱逐笔风险审核、函件、可疑交易、档案和培训记录；
6. 审计底稿附件、抽样明细、文件页码和文件哈希；
7. 经营Excel可以从有效排名序列计算参与排名营业部家数，但“剔除已撤销营业部”的原因性表述仍缺少独立机构状态或剔除名单；
8. 生产环境形成的最终复核版报告和统一复核记录。
