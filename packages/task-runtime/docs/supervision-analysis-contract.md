# 监督共享信息分析非 Java 后端契约

## 边界

- 文件中心和监督共享两个上传入口最终进入同一 OCR、解析、入库流程；`uploadEntry` 只保留来源标识。
- 分析任务只接收已固化的资料版本快照。`processing`、`failed`、`needs-metadata`、`disabled` 资料不得进入分析。
- 分析任务不执行上传、OCR、重新解析和重新入库。
- 资料范围由后端自动确定并固化，不设置资料选择、勾选或用户确认环节；前端提交任务后直接进入后台处理。
- 一项任务只允许选择一个被分析单位，可以是总部部门、子公司、分公司或营业部；资料正文中的多个涉及单位
  或责任部门不等于任务选择了多个单位。
- 候选资料先按单位唯一编码、分析期间和处理状态从结构化元数据中筛选并固化快照；关键词检索、
  BGE-M3 稠密/稀疏检索和重排只能在快照文档版本范围内执行，不允许用 RAG 扫描全库决定资料归属。
- 整改及问责关联由后端执行；精确引用或高置信唯一候选自动确认，低置信、多候选、状态冲突、未匹配进入复核。
- 统计只使用已确认问题和已确认关联。

## 输入契约

公共任务、资料快照、问题和证据的持久化映射见 `docs/shared-business-data-contract.md`。业务任务使用
`taskId`，Pi 的 `runId` 仅代表一次模型执行；一个任务可以重试并产生多个运行记录。

`supervision-analysis` 的运行 `payload` 包含：

| 字段 | 含义 |
|---|---|
| `task` | 任务编号、分析期间、唯一被分析单位 `organizationId` 和选填 `analysisDescription` |
| `snapshotAt` | 快照固化时间 |
| `materials` | 两个入口产生的资料及处理状态、解析版本、索引版本 |
| `issues` | 按提取规则形成的问题候选和证据定位 |
| `rectifications` | 整改记录及上游语义候选分数 |
| `accountabilities` | 问责记录及上游语义候选分数 |
| `continuousAsCompleted` | 持续整改是否按完成口径统计，缺省为否 |

任务字段与前端创建表单对应如下：

| 字段 | 页面含义 | 必填 |
|---|---|---|
| `taskId` | 平台生成的任务编号 | 是 |
| `organizationId` | 被分析单位唯一编码 | 是 |
| `analysisStart` / `analysisEnd` | 分析期间起止日期，`YYYY-MM-DD`，含起止日 | 是 |
| `analysisDescription` | 分析说明：分析背景和特别关注事项 | 否 |

公共任务的 `periodStart` / `periodEnd` 映射为上述起止日期。分析说明在监督扩展配置
`SupervisionTaskConfigRecord.analysisDescription` 中保存，再经适配器传给运行任务；空白按未填处理。
任务名称、负责人、参与人员等由平台维护，不作为来源筛选条件。

任务不再接收 `sourceTypes` 或 `rectificationAsOf`，也不设置来源部门范围、报告口径、关注重点和领导关注说明。
运行入口会拒绝旧任务字段；旧任务需由上游按新契约重新组装，不自动兼容或修改已有报告文件。
固定生成《监督信息汇总分析报告》，问题归类、整改、问责和日常监督等固定内容始终保留。
分析说明传入正文生成，作为背景和展开重点；它不是事实证据，不能改变期间、统计口径或省略固定章节。

## 资料匹配与 RAG 边界

执行顺序：Java/资料服务按权限获取候选资料 → 后端按单位、分析期间和处理状态自动筛选 → 固化资料版本快照 → 自动提取、关联、统计和撰写。
任务接口不接收前端勾选的文件列表或资料确认标记。结果页可以只读展示已使用资料及逐段引用，不作为生成前置步骤。

现有 Pi 的 `scopeSupervisionAnalysisPayload` 和工具集会自动执行筛选，无需确认调用；当前仍由上游通过
`payload.materials` 提供候选资料。Java/资料服务自动取数、权限过滤及快照持久化是生产对接职责，本契约不表示这些服务已完成接入。

Java 上传元数据可改用 `uploadedMaterials` + `categoryMappings` 输入，由运行入口自动转换为上述 `materials`。
两种输入互斥，上传契约和分类配置见 `docs/java-supervision-upload-contract.md`。资料来自本平台上传入口；
不要求甲方原始记录关联、甲方接口或导入记录。

1. Java 上传入口保存发文日期、类别、涉及单位唯一编码及内外部属性；这些字段优先使用上传元数据。audit-ai 提取附件业务内容，对缺失或冲突返回校验信息，不静默覆盖上传字段。单位名称与编码由组织目录映射，不根据上传部门推定被分析单位。
2. 创建任务时，后端按唯一 `organizationId`、分析期间和 `processingStatus=indexed` 查询候选资料，纳入全部支持的来源类型。
3. 无效/缺失文件日期、单位未匹配、超出期间或解析未完成的资料写入快照排除项及原因。
4. 快照返回不可变的 `documentId`、`documentVersionId` 和 `indexVersion`，作为后续 RAG 的强制过滤条件。
5. 问题候选、整改记录和问责记录必须同时属于该快照及所选单位，才可进入关联、统计和报告。
6. 问题使用 `discoveredDate`，整改和问责使用记录业务日期 `asOfDate`，未提供时使用来源文件 `fileDate`；均须在分析期间内，上传时间不参与判断。
7. 不另设整改截至日期；例如分析期间为 1 月 1 日至 6 月 30 日，7—8 月整改资料或进展均不纳入本次报告、完成率和逐段引用。

缺失或无效文件日期等不合格资料由后端记录排除原因，剩余合格资料继续分析；全部无可分析资料时返回
`readiness.status=BLOCKED`。不创建等待用户确认资料的中间状态，不把元数据缺失自动认定为符合范围。
资料范围自动化不改变问题事实、整改关联及证据的确认规则，未确认事项仍按既有规则排除出确认口径统计。

资料自身的 `sourceType`、责任部门及提取规则中的来源分类继续用于章节归类和问题关联；不是任务表单的筛选字段。

合同管理、授权管理、财务管理、反洗钱工作；允许后续通过配置扩充，不将“其他”内容强行归入现有类别。

## 自动关联顺序

1. 问题编号精确匹配，分数 `1.00`。
2. 文件文号精确匹配，分数 `0.98`。
3. 上游语义分数占 `75%`，涉及单位一致占 `15%`，责任部门一致占 `10%`。
4. 缺省自动确认阈值 `0.85`，进入复核阈值 `0.65`，前两名差距小于 `0.08` 视为多候选。
5. 同一问题的明确问题编号关联、业务日期有效的整改记录，采用分析期间内最新状态；同日冲突或不能确定更新关系时标记 `STATUS_CONFLICT`，不得自动确认。

## 输出契约

正文生成后的在线编辑文档包使用 `supervision-report-document.v1`，与下述分析结果分开。
逐段引用名称、来源追溯及 Java 对接约定见 `docs/java-supervision-report-contract.md`。

输出为 `supervision-analysis.v1` JSON，包含规则版本、任务、资料快照、问题、整改/问责关联、确认口径统计、
报告生成就绪状态和报告目录。确认问题缺证据、未知规则或报告模块与规则不一致时阻断；重点字段缺失、待确认问题、
待处理关联或资料被排除时给出告警。

## 暂无真实资料服务时的 fixture 模式

- 使用 `fixtures/supervision-analysis/dfzq-public-corpus.json` 保存东方证券相关官方公开监管资料的归一化摘要。
- `loadDfzqPublicFixturePayload` 校验官方域名、摘要 SHA-256 和模拟数据标识后，生成标准分析 payload。
- 公开监管摘要用于验证问题提取；配套整改、问责和内部问题均为明确标注的模拟数据。
- fixture 同时模拟文件中心与监督共享两个入口，但不会执行上传、OCR或实时联网请求。
- 输出的 `readiness.warnings` 会明确提示包含的模拟资料、问题和整改问责记录数量。
